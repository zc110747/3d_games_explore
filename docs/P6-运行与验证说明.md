## 1. 需求与结论对照

| # | 需求 | 落地方式 | 结果 |
|---|---|---|---|
| 1 | 默认进入主界面（原项目菜单与选择），这一步不做 3D 化；进入主界面后才 3D 化 | `#p1-legacy` 改为**整屏原版 2D**（原版 DOM / 操作 / 触摸键 / 状态栏原样保留），`#p1-stage`+`#p1-ui` 默认隐藏。`p6/ViewMode.mjs` 只读轮询 `getInputPhase().kind`：`menu`（主菜单 / 选剧本 / 选君主 / 难度 / 回合菜单）→ 2D；`zs`（战略地图选城）/`ei`（城市菜单）/`battle` → 3D | ✅ |

## 3. 相机：正面俯视的具体改动

| 项 | 旧（P1–P5） | 新（P6） |
|---|---|---|
| 方位角 / 俯角 | 45° / 45°（等距斜视） | **0° / 90°（正上方俯视）** |
| 相机 up | 固定 `(0,1,0)` | 俯角 ≥89.5° 用 `(0,0,-1)`，世界 +Z 朝屏幕下（与原版行号向下增大一致） |
| 整图取景 | `margin 1.14` | `margin 1.3` + `offsetY -0.1`（让出顶部状态条，同时不被底部按钮条压住最下排城市名） |
| 平移边界 | 固定 `panLimitX=9 / panLimitZ=7`（斜视下够用） | `max(0, 地图半幅 − 当前视野半幅)`：整图可见时**拖不出画面**，放大后才允许平移查看局部 |
| 战斗取景 | 相机 target 右移半个 HUD 宽 | 改为**投影窗口平移**（`fit(..., offsetPx)`），不占平移余量、不改逻辑坐标 |
| 旗帜 | 竖直旗布 | 水平旗布贴在杆顶（`rotation.x=-90°`），飘动只改 `rotation.z` |

`WorldCamera.getState()` / `BattleCamera.getState()` 的 `fixed45` 字段改为 **`fixedView` + `topDown`**，语义更准确（测试与调试面板同步更新）。

## 4. 操作对照：原版 `zs()` vs 3D 主界面

原版 `zs()` 的真实行为（`sgby.core.js` 实测，非推测）：

| 用户动作 | 原版行为 | 3D 实现 |
|---|---|---|
| 点击地图格（非光标所在格） | 光标移到该格（不确认） | `adapter.requestCursorTo(col,row)`，按差值逐格投递 34/35/36/37 |
| 再次点击同一格 | 该格有城则返回城市（`if(o) return o-1`），空地无反应 | `adapter.pressKey(39)`，后续完全由原版决定 |
| 方向键 / WASD | 光标上下左右 | **不拦截**，原版 `class A` 的 `window keydown` 直接消费 |
| E / Enter | 确认 | 同上（原版键码 39） |
| Q / Esc | 返回 255（回战略上层） | 同上（原版键码 40） |
| Tab / H | 帮助页 | 同上（原版键码 38）；底部「信息」按钮等价，会**临时切回原版 2D 画面**显示帮助页 |
| M | 形势图 | 同上（原版键码 51）；底部「查找」按钮等价，同样临时切回 2D 显示形势图 |
| 拖动画布 | 滚动 12×9 视口 | 相机平移（受动态边界限制，拖不出地图） |
| 滚轮 / `+` `-` | 原版无此操作 | 3D 增强：以视口中心为锚点缩放（0.6–3×） |

3D 额外补的两件**纯表现**设施：

1. **光标格高亮**：金色方框 + 淡填充标出 `Dn.g_CityPos` 所在格，城市高亮跟随原版光标（只在变化时重建道路高亮）。
2. **顶部状态条**：君主名 + 城数、年月、光标格与所在城名——全部来自 `Dn` / `lib`，不含新状态。

## 7. 遗留问题

1. **原版战斗阶段的 `kind` 仍可能落到 `menu`**（`waitMsg` 栈里出现了菜单类函数名）。当前用 `guardGame`（P4 `active` 为真时禁止切 2D）兜底，行为正确，但 `kind` 本身不够精确；后续可在 `GameAdapter` 里保留最近一次栈片段用于定位。
2. **原版帮助页 / 形势图（38 / 51）在 3D 视图下看不到**：两者由原版画到 2D 画布上，而 `game` 态该画布隐藏。按钮仍会把键码投递给原版（状态机与 2D 一致），只是画面不可见；如需完整复刻，应把 `lib.loadPic(75)` 与帮助文本渲染到 HTML 浮层。
3. **原版 `Ma()` 回合菜单**（策略结束 / 存储进度 / 结束游戏）会判为 `menu` 并切回 2D —— 这是有意的（该菜单本轮未做 3D 化）。
4. **原版整数倍缩放**：小窗口下主界面只给 ×1，画面周围留白较多；这是原版像素完美缩放策略，不是本次改动引入。
5. **帮助 / 形势图的回落是"临时显示 2D"**：投递 38/51 后自动切回原版画面并显示提示条，靠用户这一次按键/点击被原版消费来关闭（不额外补发按键，否则会变成确认选城）。若用户长时间不操作，画面会停在原版帮助页——与掌机行为一致。

**图例为什么不在左下角**：`PresentationStore.DEFAULTS.ui.p2Panel = true`，左侧 P2 调试面板**默认就是打开的**，且 `top:56px; max-height:calc(100vh-76px)` 从顶一直铺到近底部、`z-index:11`。放在 `left:16px; bottom:42px; z-index:9` 的图例被它**整块压住**——文档写着有、画面上根本看不见（截图核对时才发现）。最终放进 `#p6-ops` 的 flex 流里，位置和显隐都跟着操作条走，不需要再维护第二套规则。配套把 `_buildOps()` 的 `host.replaceChildren()` 改成只删自己生成的 `.p6-ops-group/.p6-dpad`，否则宿主里预置的图例会被一起清掉。

| 4 | `applyView` 用两层 `requestAnimationFrame` 等两帧再暂停：与"视图已切回 game"赛跑，且违反"全站只有一个自续循环"的静态校验 | 异步等待没必要 | 改成同步：`resume()` → `scenes.render()` 渲染一帧 → `pause()` |

另外修正了**性能脚本的口径错误**：`tests/perf.mjs` 原来直接开测，但 P6 起页面默认停在 2D 主界面、3D 渲染是暂停的，
测到的是"暂停后的 rAF"，会出现"空载 59fps 其实一帧没画"。现在测量前先 `__P6__.setView('game', true)` 钉住 3D 视图，
并记录应用内帧统计作为交叉校验。

### 10.2 性能：本机天花板与口径修正

环境：无头 Edge 158 + **SwiftShader 软件光栅化** + 1570×758、dpr 1。原始数据 `tests/.perf/post-merge.json`。

| 场景 | fps | mean | p95 | max | jitter | draws | tris | 堆 MB |
|---|---|---|---|---|---|---|---|---|
| idleWorld | 20.56 | 48.63 | 50.1 | 66.7 | 5.49 | 91 | 17178 | 61.28 |
| stressWorld | 19.56 | 51.14 | 50.1 | 333.3 | 26.75 | 91 | 17178 | 59.87 |
| dpr2World | 19.83 | 50.42 | 50.1 | 66.7 | 3.73 | 91 | 17178 | 73.68 |

**结论一：≈20fps 是本机环境天花板，不是本轮代码引入的问题。** 三条独立证据：

1. **CPU 每帧只花 0.468ms**（`frameStats.busyMeanMs`，`busyShare = 0.96%`），而帧间隔 p50 恰好是 **50.0ms**——正是 20fps 的整数节拍。帧时间不来自 CPU 工作量。
2. **独立 rAF 探针**（不画 3D）：渲染循环 `pause()` 时回到 16.7ms（60fps），运行时 50ms（20fps）。
3. **降负载无改善**：把 3D 对象全部隐藏仍是 23fps；像素比降到 0.5 仍是 21fps。既不是 draw call / 几何瓶颈，也不是填充率瓶颈。

**结论二：与 P7 旧代码对比无回归。** 同一台机器、同一场景测 P7 提交 `62ae442`（独立 worktree）为 **19.45fps**；合并后为 **20.56fps**。

**结论三：P7 报告里的 59.67fps 作废。** 那是 1240×610 画布、且页面停在 2D 主界面（3D 渲染已 `pause()`）时测到的 rAF 节拍——等于"一帧没画"的帧率。perf 脚本已改为测量前钉住 3D 视图，并打印应用内 `frameStats` 交叉校验（本次 `20.34fps`，与外部测得的 20.56fps 一致）。

**结论四：`dropRate 0.984` / `slowFrames 1169` 不能当回归指标。** P7 的慢帧判据以 16.67ms（60fps）为基准，在 20fps 的环境里必然把所有帧都判成慢帧。smoke 的长跑断言已改成相对衰减：`长跑后 fps >= 长跑前 × 0.8`，外加 `>= 12fps` 兜底，明细里同时打印前后帧率、CPU 耗时与全屏层清单。

**结论五：自适应像素比在真实压力下确实会动作**，不是摆设。dpr=2 时 `cap` 按 `2 → 1.5 → 1` 连降两档，理由 `p95 100ms > 22ms（严重，降两档）`。

**不可测项（如实标注）**：GPU 帧时间与显存浏览器不暴露（`gpu.measurable = false`，`EXT_disjoint_timer_query` 存在但本项目不使用以避免影响渲染路径）；`performance.memory` 仅 Chromium 系可用。

### 10.3 本轮修掉的两个静默失败

| # | 现象 | 为什么测试没抓到 | 修复 |
|---|---|---|---|
| 1 | `RoadRenderer.highlightNeighbors` 抛 `ReferenceError: THREE is not defined`（一次回归中触发 11 次），选中城市时"相邻路径高亮"**实际从未画出来** | ① `smoke` 只在**启动时**查一次 `exceptions.length === 0`，交互期异常只打印、不参与判定；② `getDiagnostics().highlighted` 只数 `links` 里符合条件的边数，**根本不看 `_highlight` Mesh 是否存在** → 断言照样 PASS | 方法内补 `const THREE = this.THREE`（该模块约定 THREE 由构造函数注入，`build()` 本来就这么写）；`getDiagnostics()` 新增 `highlightMesh` / `highlightVertices`；smoke 新增「高亮路径真的生成了 Mesh」「全程无页面 JS 异常」两条断言 |
| 2 | `CityRenderer.getDiagnostics().factions` 统计失真 | 用了 `build()` 时的 `cities` 快照，而 `refreshCity()` 更新的是 `_byId` | 改为遍历 `this._byId.values()` |
| 3 | 阵营图例文档写着"左下角"，**画面上完全看不见** | 没有断言检查"图例是否真的可见"；左侧调试面板默认打开且盖满左侧 | 图例移进 `#p6-ops` 操作条；`_buildOps()` 的 `replaceChildren()` 改为只删自己生成的组；smoke 增加"在操作条内 + 三色精确 + 尺寸非零"断言 |
| 4 | 顶栏一度显示「整合 · 不一致 1 项」红字 | 该红字来自每秒重算的 `cachedConsistency`，但**没有任何断言盯着它**，只在别处单独调 `consistency()` 且恰好都通过 | 主循环把每次失配文案记进 `consistencyLog`（去连续重复、上限 24），`getSnapshot()` 暴露，smoke 末尾断言其为空 |

教训：**"算出了要亮几条边"≠"真的画出来了"**；同理 **"数据里一致"≠"界面上没写红字"**。凡是"逻辑判断 + 渲染产物"两段式的功能，断言必须落在渲染产物上（Mesh 是否存在、顶点数是否 > 0、DOM 是否可见）；凡是界面上的状态提示，断言必须盯着**那个提示本身**。

> 关于第 4 条的如实说明：加入 `consistencyLog` 后连续 2 次完整回归（每次 171 项）都是「全程未出现失配」，**未能复现**那一帧红字，因此不宣称"已修复"。记录器保留，此后任何一次出现都会让测试直接 FAIL 并打印具体文案。
