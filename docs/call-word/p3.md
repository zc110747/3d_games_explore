# P3：三国霸业3D重制项目——城市管理UI与武将选择系统

## 一、阶段目标

基于P0原版项目调研、P1基础架构和P2三维战略地图，实现完整的城市管理界面。

本阶段将原版城市管理菜单迁移为HTML/CSS界面，保留原版功能、操作顺序、数据结构和游戏规则。

主要完成：

1. 点击己方城市后进入城市管理界面。
2. 实现城市管理界面的整体布局。
3. 左侧实现纵向功能按钮。
4. 右侧实现对应功能内容面板。
5. 实现武将列表和完整独立的武将选择弹窗。
6. 实现原版城市管理功能的交互。
7. 实现城市信息展示。
8. 实现城市管理操作与原版游戏逻辑同步。
9. 实现城市管理界面与3D战略地图之间的场景交互。
10. 实现关闭、返回和取消等操作。

本阶段不开发战斗地图和战斗动画。

## 二、核心设计原则

### 2.1 原版功能优先

原版游戏是唯一的业务逻辑来源。

必须通过P0阶段的源码分析，逐一确认原版城市管理菜单的全部功能。

包括但不限于：
- 城市信息。
- 内政管理。
- 城市建设。
- 资源管理。
- 武将管理。
- 军事管理。
- 征兵。
- 训练。
- 城防。
- 其他原版实际存在的功能。

以上仅为功能类别示例，最终以原版真实代码为准。

不得因为现代化UI设计而删除原版功能。

不得自行添加会改变游戏规则的新功能。

### 2.2 UI与业务逻辑分离

HTML/CSS负责界面展示和交互。

GameAdapter负责调用原版游戏逻辑。

UI不得直接修改原版游戏状态。

操作流程：

用户点击UI
    ↓
UI组件收集操作参数
    ↓
GameAdapter调用原版接口
    ↓
原版游戏逻辑执行
    ↓
获取实际执行结果
    ↓
刷新UI数据
    ↓
同步更新3D地图

不得在前端UI中复制原版的资源计算、武将分配、操作限制和其他游戏规则。

### 2.3 操作流程一致

必须保留原版的：
- 功能分类。
- 功能顺序。
- 操作步骤。
- 可操作条件。
- 参数输入方式。
- 武将选择规则。
- 操作结果。
- 错误提示和限制条件。

如果原版某项操作需要多个步骤，新UI必须保留对应的操作过程。

## 三、城市管理界面整体布局

采用HTML/CSS覆盖在3D战略地图之上的UI层。

### 3.1 整体布局

建议采用以下结构：

┌────────────────────────────────────────────┐
│                 城市信息栏                  │
├──────────┬─────────────────────────────────┤
│          │                                 │
│  功能    │                                 │
│  按钮    │          功能内容面板            │
│          │                                 │
│  内政    │                                 │
│  军事    │                                 │
│  人事    │                                 │
│  其他    │                                 │
│          │                                 │
├──────────┴─────────────────────────────────┤
│              返回 / 关闭区域                │
└────────────────────────────────────────────┘

具体布局和功能分类必须结合原版实际操作流程确定，不得直接照搬示意图中的分类。

### 3.2 城市信息栏

显示当前选中城市的真实信息。

根据原版实际数据决定显示字段，例如：
- 城市名称。
- 所属势力。
- 当前君主。
- 城市资金。
- 粮食。
- 人口。
- 军队。
- 城防。
- 武将数量。

不得显示原版不存在的数据。

要求：
- 城市名称突出显示。
- 资源数据清晰。
- 数值实时同步。
- 城市信息发生变化后自动刷新。

### 3.3 左侧功能按钮

按照原版菜单功能和顺序组织按钮。

要求：
- 纵向排列。
- 当前选中功能有明显高亮。
- 不可用功能按照原版规则显示为禁用状态。
- 点击功能按钮切换右侧内容。
- 保留原版功能的名称和含义。
- 按钮不能绕过原版操作条件。

### 3.4 右侧功能内容面板

根据当前功能动态显示对应操作界面。

例如：
- 资源信息和操作。
- 武将列表。
- 军事操作。
- 城市建设。
- 内政管理。

具体面板根据P0分析得到的原版功能清单逐一实现。

要求：
- 面板之间相互独立。
- 切换功能时正确刷新数据。
- 不重复执行原版操作。
- 取消操作不修改游戏数据。
- 操作完成后显示原版返回结果。

## 四、城市管理功能迁移

### 4.1 功能清单

开始开发前，必须将P0分析得到的原版城市菜单与新UI建立映射表。

建议格式：

| 原版功能 | 原版调用入口 | 新UI组件 | 状态 |
|---|---|---|---|
| 功能A | 真实源码接口 | 对应面板 | 待实现 |
| 功能B | 真实源码接口 | 对应面板 | 待实现 |

不得凭经验猜测原版接口。

### 4.2 功能调用

每个UI功能必须具备完整的调用链：

1. 用户选择功能。
2. 显示对应功能面板。
3. 读取当前城市和相关数据。
4. 用户输入或选择参数。
5. 执行原版操作。
6. 获取原版返回结果。
7. 更新城市信息。
8. 更新武将和资源信息。
9. 同步更新3D战略地图。

### 4.3 操作限制

必须遵守原版的：
- 城市归属限制。
- 武将状态限制。
- 资源限制。
- 操作次数限制。
- 回合限制。
- 功能开放条件。

如果操作不允许执行，应按照原版行为提示用户。

不得由UI自行判断后绕过业务层。

### 4.4 操作结果反馈

操作执行后，根据原版实际结果显示：
- 执行成功。
- 执行失败。
- 资源不足。
- 条件不满足。
- 其他原版提示信息。

不得虚构操作成功结果。

## 五、武将管理与选择系统

武将选择是本阶段重点功能。

### 5.1 武将列表

根据原版实际数据展示当前城市的武将。

可展示的字段包括：
- 武将姓名。
- 武力。
- 智力。
- 统率（如果原版存在）。
- 忠诚度。
- 当前状态。
- 所属势力。
- 其他原版属性。

不得擅自创造原版不存在的属性。

要求：
- 支持列表滚动。
- 当前选择状态明显。
- 武将数据来自GameAdapter。
- 武将状态变化后刷新列表。

### 5.2 独立武将选择弹窗

武将选择使用完整独立弹窗，不要直接挤在城市管理主面板中。

弹窗建议包含：

- 弹窗标题。
- 武将列表。
- 武将属性详情。
- 当前选择状态。
- 确认按钮。
- 取消按钮。

### 5.3 选择流程

1. 打开武将选择弹窗。
2. 读取原版允许选择的武将。
3. 显示武将列表。
4. 点击武将查看详细属性。
5. 选择一个或多个武将（根据原版操作要求）。
6. 点击确认。
7. 调用GameAdapter对应原版接口。
8. 根据原版执行结果更新界面。

取消时：
- 关闭弹窗。
- 不修改武将归属或状态。
- 保留原本游戏状态。

### 5.4 武将选择规则

必须遵守原版：
- 武将所属城市。
- 武将所属势力。
- 武将是否在执行其他任务。
- 武将是否可被调动。
- 武将是否允许参与当前操作。
- 单次允许选择数量。
- 其他限制。

如果原版没有某项限制，不得自行增加。

### 5.5 武将弹窗交互

要求：
- 弹窗位于最上层。
- 背景适当遮罩。
- 禁止点击穿透到3D地图。
- 支持取消。
- 支持确认。
- 支持滚动。
- 支持查看武将详细信息。
- 关闭弹窗时正确释放临时状态。

## 六、3D地图与城市UI联动

### 6.1 进入城市管理界面

用户在3D战略地图点击城市后：

1. 判断原版是否允许进入该城市管理界面。
2. 调用原版城市选择逻辑。
3. 获取实际选中的城市。
4. 判断城市是否为玩家可管理城市。
5. 如果允许管理，打开城市管理UI。
6. 显示当前城市信息。

对于敌方城市或空城，必须根据原版实际规则处理，不得强制打开玩家城市管理界面。

### 6.2 城市切换

如果原版允许在城市管理过程中切换城市：

- 更新当前城市ID。
- 更新城市信息。
- 更新武将列表。
- 更新功能可用状态。
- 更新3D地图选中效果。

不得出现UI显示一个城市，而GameAdapter实际操作另一个城市的情况。

### 6.3 退出城市管理

退出后：
- 关闭城市管理面板。
- 关闭未完成的弹窗。
- 清理临时选择状态。
- 返回3D战略地图。
- 保留原版真实游戏状态。
- 恢复正常地图交互。

## 七、UI视觉设计

参考经典三国策略游戏的界面风格。

建议：
- 中国古代风格。
- 深色木质或石质面板。
- 古典纹理。
- 金色装饰线。
- 清晰的按钮状态。
- 统一字体和图标。
- 适度使用半透明背景。

整体风格应与3D战略地图协调。

### 7.1 视觉层级

需要区分：
- 城市名称。
- 资源信息。
- 功能按钮。
- 当前操作内容。
- 弹窗。
- 操作提示。

### 7.2 分辨率适配

支持桌面浏览器窗口变化。

要求：
- 面板尺寸自适应。
- 不遮挡关键功能。
- 武将列表能够正常滚动。
- 弹窗不会超出屏幕。
- 不影响3D场景尺寸同步。

本阶段优先保证桌面端使用体验。

## 八、架构和代码要求

优先复用现有UI框架和项目结构。

如果项目尚无合适的UI组件结构，可根据现有技术栈建立：

- CityManagementUI：城市管理界面入口。
- CityInfoPanel：城市信息栏。
- CityActionMenu：左侧功能菜单。
- CityActionPanel：右侧功能面板。
- OfficerList：武将列表。
- OfficerSelectDialog：武将选择弹窗。
- OperationDialog：操作确认和结果提示。
- CityUIAdapter：城市UI与GameAdapter之间的适配层。

上述组件名称为建议，不要求机械照搬。

要求：
1. 组件职责清晰。
2. UI组件不直接修改原版游戏数据。
3. 通过GameAdapter调用原版接口。
4. 不重复实现原版业务规则。
5. 不重复维护权威游戏状态。
6. 支持城市状态变化后局部刷新。
7. 支持弹窗关闭和组件销毁。
8. 不影响P1和P2已经完成的功能。

# 十二、阶段执行约束

1. 只实施当前指定阶段的任务。
2. 不提前开发后续阶段的功能。
3. 开始前检查P0、P1和P2阶段的交付物。
4. 以真实源码为依据，不猜测原版接口。
5. 优先复用现有代码。
6. 不允许修改无关的原版逻辑。
7. 不允许用模拟数据代替原版数据。
8. 当前阶段必须实现实际功能，而不是只输出方案。
9. 完成后运行相关测试。
10. 对照阶段验收标准逐项检查。
11. 记录实际修改的文件和接口。
12. 记录尚未解决的问题。
13. 保持项目可以正常启动和运行。
14. 不得以TODO或空函数冒充完成。
15. 如果发现原版行为与预期不一致，先分析并报告，不得自行改变游戏规则。

阶段结束时输出：

- 完成内容。
- 修改文件。
- 新增接口。
- 测试结果。
- 验收情况。
- 遗留问题。
- 下一阶段前置条件。

不得擅自进入下一阶段，等待用户确认后再继续。
