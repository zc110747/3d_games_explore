# P6：全局整合、场景切换与存档兼容

## 一、阶段目标

本阶段对 P1～P5 已经完成的功能进行全局整合，使项目从多个独立功能模块组合成一个完整、连贯、可以正常游玩的 3D 游戏。

本阶段重点解决：

1. 统一游戏启动入口和初始化流程。
2. 统一游戏状态管理和数据同步。
3. 实现战略地图、城市管理、战斗场景之间的完整切换。
4. 确保城市管理操作正确影响战略地图。
5. 确保战斗结果正确返回战略地图。
6. 确保原版游戏逻辑和存档系统保持兼容。
7. 统一全局 UI、事件管理、资源管理和场景生命周期。
8. 修复 P1～P5 整合后出现的接口、状态和生命周期问题。

最终要求：

项目启动后能够从新游戏开始，完成战略地图操作、城市管理、回合推进、战斗、战斗结束、返回战略地图、保存游戏和读取游戏的完整流程。

注意：

原版游戏逻辑仍然是唯一权威。

本阶段只进行架构整合和必要修复，不重新实现原版游戏规则。

## 二、开始前检查

开始开发前，必须检查以下内容：

### 1. P1 基础架构

检查：

- Three.js 是否正常初始化。
- RenderManager 是否正常运行。
- SceneManager 是否正常管理场景。
- CameraManager 是否正常工作。
- GameAdapter 是否正确连接原版逻辑。
- EventManager 是否正常发布和订阅事件。
- CoordinateSystem 是否统一管理坐标转换。
- AssetManager 是否正确管理资源生命周期。
- InputManager 是否正确处理输入。

### 2. P2 战略地图

检查：

- 原版城市数据是否正确加载。
- 城市位置是否与原版一致。
- 城市之间的连接关系是否正确。
- 城市所属势力是否正确。
- 城市旗帜是否正确显示。
- 城市点击是否能够调用原版逻辑。
- 城市状态变化是否能够更新 3D 表现。

### 3. P3 城市管理

检查：

- 城市管理界面是否正常打开和关闭。
- 城市功能菜单是否完整。
- 城市操作是否调用原版逻辑。
- 武将列表和选择界面是否正常。
- 城市操作结果是否正确反馈到原版游戏状态。

### 4. P4、P5 战斗系统

检查：

- 战斗地图是否正确加载。
- 地形、格子和单位是否正确显示。
- 移动范围和攻击范围是否来自原版算法。
- 单位选择是否正常。
- 移动和攻击是否调用原版逻辑。
- 动画是否与原版操作结果保持一致。
- 回合结束和战斗结束是否正常。
- 战斗结果是否能够正确返回原版游戏状态。

如果前置阶段存在未完成的功能，先记录具体问题，不得通过伪造数据掩盖问题。

## 三、统一游戏运行入口

整理游戏的整体启动流程。

要求：

1. 统一游戏初始化入口。
2. 避免多个模块重复初始化 Three.js。
3. 避免多个模块重复创建渲染循环。
4. 统一管理游戏运行状态。
5. 统一管理场景切换。
6. 统一管理全局事件。
7. 统一管理资源释放。

建议采用以下初始化顺序：

原版游戏初始化
    ↓
GameAdapter 初始化
    ↓
EventManager 初始化
    ↓
AssetManager 初始化
    ↓
RenderManager 初始化
    ↓
CameraManager 初始化
    ↓
SceneManager 初始化
    ↓
InputManager 初始化
    ↓
UIManager 初始化
    ↓
进入战略地图
    ↓
启动游戏主循环

具体初始化顺序以项目实际依赖关系为准。

不得为了符合上述示意顺序而破坏现有模块的初始化要求。

## 四、统一场景管理

对所有场景进行统一管理。

### 1. 场景结构

至少包含：

WorldMapScene
    战略地图场景

CityManagementScene
    城市管理场景或城市管理 UI 覆盖层

BattleScene
    战斗场景

如果 P3 的城市管理已经采用 HTML/CSS 覆盖层方式，则继续沿用，不要为了统一形式而强行改成 Three.js 场景。

### 2. 场景生命周期

每个场景必须具有清晰的生命周期：

- initialize：初始化场景。
- enter：进入场景。
- update：更新场景。
- render：执行场景表现更新。
- exit：退出场景。
- dispose：释放场景资源。

根据现有架构决定是否拆分这些接口，但必须保证生命周期完整。

### 3. 场景切换流程

实现以下流程：

流程 A：战略地图 → 城市管理

1. 点击城市。
2. 调用原版城市选择逻辑。
3. 确认当前城市状态。
4. 打开城市管理界面。
5. 显示当前城市信息。
6. 执行城市管理操作。
7. 关闭城市管理界面。
8. 返回战略地图。
9. 更新城市显示状态。

流程 B：战略地图 → 战斗

1. 原版逻辑触发战斗。
2. 获取原版战斗初始化数据。
3. 保存当前战略地图表现状态。
4. 初始化 BattleScene。
5. 加载原版战斗地图。
6. 加载战斗单位。
7. 进入战斗。

流程 C：战斗 → 战略地图

1. 战斗结束。
2. 获取原版最终战斗结果。
3. 确认原版游戏状态已经更新。
4. 释放战斗场景中的临时资源。
5. 返回战略地图。
6. 根据最新原版数据更新城市、武将、势力和单位表现。
7. 恢复战略地图的合理显示状态。

注意：

场景切换不能直接修改原版游戏状态。

战斗胜负、城市归属、武将伤亡等结果必须由原版逻辑决定。

## 五、统一游戏状态管理

建立统一的游戏状态访问和同步机制。

### 1. GameAdapter

GameAdapter 是 3D 表现层访问原版游戏数据的统一入口。

所有场景必须通过 GameAdapter 获取游戏数据。

禁止：

- 在不同场景中直接访问原版内部全局变量。
- 在前端建立另一套独立的游戏业务状态。
- 通过复制数据形成多个权威数据源。
- 在 UI 中直接修改原版游戏数据。

### 2. 状态同步

至少覆盖以下数据：

- 当前游戏阶段。
- 当前玩家。
- 当前回合。
- 城市数据。
- 城市所属势力。
- 城市资源和状态。
- 武将数据。
- 武将所属城市。
- 武将属性和兵力。
- 战斗地图。
- 战斗单位。
- 战斗单位位置。
- 战斗单位兵力。
- 战斗行动状态。
- 战斗结果。

### 3. 事件同步

使用 EventManager 统一传递状态变化。

根据原版真实操作入口建立事件映射。

例如：

CITY_SELECTED
CITY_UPDATED
CITY_OWNER_CHANGED
OFFICER_UPDATED
OFFICER_TRANSFERRED
TURN_CHANGED
BATTLE_STARTED
BATTLE_UNIT_MOVED
BATTLE_UNIT_ATTACKED
BATTLE_FINISHED
GAME_STATE_UPDATED

事件名称可以根据现有项目规范调整。

要求：

- 原版状态变化后，及时通知表现层。
- 不允许仅依赖每帧全量轮询。
- 不允许重复发布相同状态事件造成无效刷新。
- 事件监听器必须有明确的注册和注销过程。
- 场景退出时注销不再需要的监听器。
- 避免场景切换后出现重复事件处理。

如果原版没有事件机制，可以在原版操作入口外部包装事件，不要大规模修改原版逻辑。

### 4. 状态一致性

重点验证：

- 城市管理操作后，战略地图显示正确。
- 武将调动后，城市武将列表正确。
- 势力变化后，城市旗帜正确。
- 战斗后，武将兵力和伤亡正确。
- 战斗后，城市归属正确。
- 回合变化后，当前玩家和游戏阶段正确。
- 读取存档后，所有场景状态正确。

## 六、战略地图与城市管理整合

完成 P2 和 P3 的整合。

要求：

1. 战略地图始终使用原版城市数据。
2. 城市管理界面显示当前选中城市的数据。
3. 城市管理操作调用原版逻辑。
4. 操作完成后及时同步城市信息。
5. 关闭城市管理界面后，战略地图恢复正常交互。
6. 城市旗帜、名称、势力颜色正确更新。
7. 城市选择状态和 UI 选择状态一致。
8. 不允许因为打开或关闭 UI 而重置原版城市状态。

重点检查：

- 城市建设。
- 城市资源变化。
- 武将任免。
- 武将调动。
- 城市防御。
- 城市所属势力变化。
- 原版实际存在的其他城市操作。

具体功能以原版实际支持的功能为准，不得自行添加或删减。

## 七、战略地图与战斗系统整合

完成 P2、P4、P5 的整合。

要求：

1. 战略地图能够正常进入战斗。
2. 战斗初始化数据来自原版。
3. 战斗地图、地形和单位数据正确。
4. 战斗操作调用原版逻辑。
5. 战斗动画不改变原版业务状态。
6. 战斗结束后正确更新原版游戏状态。
7. 战略地图正确显示战斗结果。
8. 战斗场景退出后正确释放资源。

特别检查：

- 战斗中断。
- 战斗胜利。
- 战斗失败。
- 单位死亡。
- 武将死亡。
- 兵力变化。
- 城市易主。
- 战斗结束后的回合状态。

不得使用模拟战斗结果替代原版战斗结果。

## 八、存档与读档兼容

这是本阶段的重点内容。

必须完整分析原版存档系统。

### 1. 原版存档格式

检查：

- 原版存档格式。
- 存档文件结构。
- 存档字段。
- 存档版本。
- 保存入口。
- 读取入口。
- 初始化流程。
- 存档中的游戏状态。
- 是否存在全局变量或运行时状态需要重新初始化。

### 2. 保持原版存档兼容

要求：

1. 保留原版存档格式。
2. 保留原版存档字段。
3. 保留原版存档读取方式。
4. 保留原版存档保存方式。
5. 不随意修改存档结构。
6. 不将 Three.js 对象写入原版存档。
7. 不将模型、材质、纹理等渲染对象写入存档。
8. 不因 3D 化而破坏旧存档。

原版存档必须继续由原版存档系统负责。

### 3. 3D 表现配置

如果确实需要保存 3D 表现配置，例如：

- 战略地图相机位置。
- 战略地图缩放等级。
- UI 显示偏好。
- 音效和画面设置。

可以建立独立的表现配置存储。

该配置必须与原版游戏存档分离。

不得让 3D 表现配置成为游戏业务状态的权威来源。

### 4. 存档测试

至少完成：

- 原版新游戏保存。
- 原版新游戏读取。
- 原版旧存档读取。
- 城市管理后保存和读取。
- 战略回合推进后保存和读取。
- 战斗前保存和读取。
- 战斗结束后保存和读取。
- 读取存档后重新进入城市管理。
- 读取存档后重新进入战斗。

如果原版存档存在兼容限制，必须明确记录，不得自行改变原版格式来绕过问题。

## 九、全局 UI 整合

统一游戏 UI 的显示和交互管理。

检查：

- 战略地图 UI。
- 城市管理 UI。
- 武将选择 UI。
- 战斗 UI。
- 战斗操作按钮。
- 回合信息。
- 当前玩家信息。
- 消息提示。
- 确认和取消弹窗。
- 战斗结果界面。

要求：

1. UI 不得遮挡必要的游戏操作区域。
2. UI 显示的数据必须来自真实游戏状态。
3. 场景切换时正确显示和隐藏对应 UI。
4. 不允许多个场景重复创建相同全局 UI。
5. 关闭弹窗后正确恢复底层交互。
6. 防止鼠标事件穿透 UI 触发 3D 场景操作。
7. 不允许出现多个重复的事件监听器。

保持 P2、P3、P5 已经确定的交互设计，不要在本阶段重新设计整个 UI。

## 十、资源和生命周期管理

统一管理 Three.js 资源。

重点检查：

- Scene。
- Camera。
- Renderer。
- Geometry。
- Material。
- Texture。
- GLTF/GLB 模型。
- AnimationMixer。
- EventListener。
- Timer。
- WebSocket 或其他通信对象（如果项目存在）。

要求：

1. 场景退出时释放临时资源。
2. 可复用资源由 AssetManager 统一缓存。
3. 不允许重复加载相同模型。
4. 不允许场景销毁时误释放全局共享资源。
5. 不允许场景反复切换导致显存持续增长。
6. 不允许事件监听器重复注册。
7. 统一管理渲染循环。
8. 避免多个 requestAnimationFrame 循环同时运行。

需要明确区分：

全局资源
场景资源
临时资源

根据资源所有权决定释放时机。

## 十一、异常处理与恢复

重点处理以下异常：

1. 场景初始化失败。
2. 模型加载失败。
3. 纹理加载失败。
4. 战斗初始化失败。
5. 战斗结束时状态同步失败。
6. UI 初始化失败。
7. 存档读取失败。
8. 存档数据不完整。
9. 场景切换过程中重复触发。
10. 用户快速重复点击操作。
11. 动画尚未结束时触发其他操作。
12. 场景退出后仍然收到事件。

要求：

- 错误信息明确。
- 不允许出现无法恢复的黑屏。
- 不允许出现无限循环切换场景。
- 不允许出现游戏状态与表现状态永久不一致。
- 能够恢复的错误必须提供合理恢复流程。
- 无法恢复的错误必须明确提示用户。

不得通过忽略异常来伪装系统正常运行。

## 十三、P6 验收标准

必须满足以下要求：

1. 游戏能够正常启动。
2. 能够进入战略地图。
3. 城市管理能够正常打开和关闭。
4. 城市操作能够正确调用原版逻辑。
5. 能够正常进入战斗。
6. 战斗地图和单位数据正确。
7. 战斗能够完成。
8. 能够正确返回战略地图。
9. 战斗结果正确同步。
10. 战略回合能够正常推进。
11. 原版存档能够正常保存和读取。
12. 原版旧存档兼容性得到验证。

14. 不存在明显的场景切换资源泄漏。
15. 不存在明显的重复事件监听。
16. 不存在多个渲染循环。
17. 不存在多个权威游戏状态。
18. 所有核心操作仍然遵循原版游戏规则。

P6 完成后，项目应当具备完整的游戏流程。

如果存在无法完成的验收项，必须明确说明原因和实际完成情况，不得直接标记通过。

- EventManager 事件结构。
- UI 管理结构。
