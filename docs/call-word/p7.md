# P7：完整回归测试、性能优化、稳定性与最终视觉完善

## 一、阶段目标

本阶段是整个项目的最终质量验收阶段。

在 P1～P6 已经完成的基础上，对整个游戏进行全面检查、回归测试、性能优化、稳定性优化和视觉完善。

本阶段不再开发新的大型功能，不重新设计游戏架构，不改变原版游戏规则。

核心目标：

1. 验证完整游戏流程是否正常。
2. 验证 3D 表现与原版游戏逻辑是否一致。
3. 验证城市、武将、势力、战斗和回合数据是否正确。
4. 验证原版存档兼容性。
5. 修复场景切换和资源管理问题。
6. 优化 Three.js 渲染性能。
7. 优化模型、材质、光照、动画和视觉效果。
8. 优化 UI 布局、交互反馈和文字可读性。
9. 验证不同浏览器、屏幕尺寸和高 DPI 环境下的运行情况。
10. 形成完整的项目验收报告。

最终要求：

项目应当具备稳定、完整、可持续运行的游戏体验。

本阶段以发现问题、修复问题、验证结果为主，不得为了追求视觉效果破坏原版游戏逻辑。

对比：

- 城市坐标。
- 城市所属势力。
- 城市连接关系。
- 武将 ID。
- 武将所属城市。
- 武将属性。
- 当前玩家。
- 当前回合。

### 2. 战斗数据一致性

对比：

- 地图宽高及实际格子结构。
- 地形数据。
- 单位 ID。
- 单位兵种。
- 单位位置。
- 单位兵力。
- 移动范围。
- 攻击范围。
- 行动状态。
- 伤害结果。
- 战斗结束状态。

### 3. 操作结果一致性

选择具有代表性的操作，分别记录：

原版执行前状态
原版执行操作
原版执行后状态
3D 表现更新后状态

比较两者是否一致。

建议建立自动化数据快照或测试辅助工具。

但注意：

- 快照只能用于测试。
- 测试辅助工具不得成为新的游戏数据来源。
- 不得修改原版逻辑来适配测试工具。
- 不得用模拟数据代替实际游戏数据。

### 4. 误差和异常处理

对于坐标转换、浮点数和 3D 渲染产生的表现误差，应区分：

- 逻辑数据误差。
- 坐标映射误差。
- 屏幕显示误差。
- 模型视觉误差。

逻辑数据应保持精确一致。

视觉坐标可以使用合理的浮点容差，但不能以视觉容差掩盖逻辑错误。

## 五、Three.js 性能优化

对整个 3D 渲染系统进行性能分析。

先建立基准测试，再根据实际瓶颈优化。

不要在没有性能数据的情况下盲目修改渲染架构。

### 1. 性能指标

至少记录：

- FPS。
- 平均帧时间。
- 帧时间波动。
- CPU 使用情况（可获得时）。
- GPU 使用情况（可获得时）。
- Draw Calls。
- 三角形数量。
- 活跃 Geometry 数量。
- 活跃 Material 数量。
- 纹理数量。
- 纹理显存估算。
- 场景加载时间。
- 场景切换时间。
- 内存变化。
- 长时间运行后的资源增长。

对于浏览器无法直接获取的指标，明确标注不可直接测量，不得伪造数据。

### 2. 渲染优化

重点检查：

- 是否存在重复渲染。
- 是否存在不必要的对象更新。
- 是否每帧重复创建 Geometry。
- 是否每帧重复创建 Material。
- 是否每帧重复创建临时对象。
- 是否存在大量无效事件处理。
- 是否存在不必要的阴影计算。
- 是否存在不必要的透明材质。
- 是否存在过度复杂的模型。

根据实际情况使用：

- InstancedMesh。
- Geometry 复用。
- Material 复用。
- Texture 复用。
- Frustum Culling。
- 合理的阴影策略。
- 合理的纹理分辨率。
- 合理的像素比限制。
- 静态对象更新优化。

不能为了减少 Draw Calls 而破坏模型层次、拾取逻辑或动画效果。

### 3. 相机和屏幕优化

检查：

- 不同分辨率下的相机表现。
- 高 DPI 屏幕。
- 浏览器窗口缩放。
- 窗口大小变化。
- 战略地图缩放。
- 战斗地图缩放。
- UI 与 3D 场景的尺寸同步。

避免设备像素比过高导致 GPU 负载异常。

### 4. 长时间运行测试

至少进行一次连续运行测试。

重点观察：

- 内存是否持续增长。
- GPU 资源是否持续增长。
- 事件监听器是否累积。
- 场景切换后是否残留对象。
- 动画是否逐渐卡顿。
- WebSocket 或其他连接是否异常累积（如果项目存在）。

如果发现内存增长，区分正常缓存和无法释放的资源泄漏。

## 六、稳定性与异常恢复

重点测试以下情况：

1. 连续打开和关闭城市管理界面。
2. 连续进入和退出战斗。
3. 快速重复点击城市。
4. 快速重复选择战斗单位。
5. 动画播放期间重复输入。
6. 模型加载失败。
7. 纹理加载失败。
8. 存档读取失败。
9. 存档数据不完整。
10. 战斗初始化失败。
11. 战斗结束时场景切换失败。
12. 窗口尺寸变化。
13. 浏览器切换标签页后恢复。
14. 浏览器刷新。
15. WebGL 上下文丢失及恢复。

重点检查 WebGL Context Lost：

- 能否检测上下文丢失。
- 能否停止无效渲染。
- 能否在上下文恢复后重建必要资源。
- 无法自动恢复时是否提供明确提示。
- 是否会造成游戏逻辑状态丢失。

注意：

WebGL 上下文恢复属于渲染层恢复问题，不应重新初始化或重置原版游戏业务状态。

如果某项恢复能力受浏览器或现有架构限制，必须记录实际限制。
