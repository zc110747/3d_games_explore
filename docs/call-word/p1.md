# P1：三国霸业3D重制项目——Three.js接入与基础架构搭建

## 一、阶段目标

基于P0阶段完成的原版项目调研报告，开始实施三国霸业3D重制项目的基础架构。

本阶段主要完成：

1. 将Three.js接入现有项目。
2. 建立统一的3D渲染管理体系。
3. 建立原版游戏逻辑适配层。
4. 建立统一的游戏状态读取和事件同步机制。
5. 建立统一的坐标转换体系。
6. 建立战略地图、城市管理、战斗三个场景的管理框架。
7. 建立3D资源管理机制。
8. 建立基本输入和交互管理机制。

本阶段不实现完整游戏场景，重点是建立可靠、可扩展、与原版逻辑解耦的技术基础。

## 二、项目设计原则

### 2.1 原版逻辑优先

现有原版游戏逻辑是唯一权威。

Three.js只负责：
- 3D场景。
- 3D模型。
- 纹理。
- 摄像机。
- 动画。
- 3D拾取。
- 视觉反馈。

原版游戏逻辑负责：
- 游戏状态。
- 城市数据。
- 武将数据。
- 势力数据。
- 城市操作。
- 战略行动。
- 战斗规则。
- 回合推进。
- 存档。

不得在Three.js中重新实现游戏规则。

### 2.2 最小侵入原则

优先通过适配层接入原版游戏。

不得为了引入Three.js而大规模修改原版代码。

如果原版逻辑与UI存在耦合：
- 优先通过适配器包装现有函数。
- 必要时增加最小范围的接口。
- 保留原版调用方式。
- 不修改原版业务计算。

### 2.3 架构可扩展

后续需要支持：

- 3D战略地图。
- 3D城市展示。
- 伪3D战斗地图。
- 多种3D模型。
- 城市旗帜。
- 部队动画。
- UI弹窗。
- 场景切换。

不得针对单一城市或单一战斗场景硬编码架构。

## 三、Three.js接入

### 3.1 依赖接入

根据P0分析结果，选择合适的Three.js接入方式。

要求：
- 兼容当前项目运行环境。
- 尽可能沿用当前构建工具。
- 不无必要更换前端框架。
- 不破坏原版游戏启动流程。
- 依赖版本明确。
- 资源加载路径统一。

如果项目使用原生JavaScript，则优先采用原有模块体系接入。

如果项目已经使用Vite、Webpack或其他构建工具，则优先沿用。

### 3.2 渲染管理器

建立统一的RenderManager。

负责：
- WebGLRenderer初始化。
- Canvas管理。
- 场景渲染。
- 窗口尺寸变化。
- 像素比例控制。
- 渲染循环。
- 渲染资源释放。

要求：
- 整个应用尽量复用一个WebGLRenderer。
- 场景切换时不重复创建Renderer。
- 正确处理窗口缩放。
- 提供统一的渲染入口。
- 支持暂停和恢复渲染。
- 避免重复注册动画循环。

### 3.3 基础渲染配置

建立统一配置：

- 背景颜色。
- 抗锯齿。
- 色彩空间。
- 色调映射。
- 像素比例。
- 阴影配置。

根据目标运行环境选择合理参数，不要在本阶段追求复杂光照效果。

## 四、游戏逻辑适配层

这是P1最重要的模块。

建立GameAdapter，负责Three.js与原版游戏逻辑之间的通信。

### 4.1 适配层职责

负责：
- 读取原版游戏状态。
- 读取城市数据。
- 读取武将数据。
- 读取势力数据。
- 调用原版城市选择接口。
- 调用原版城市操作接口。
- 读取战斗状态。
- 调用原版战斗操作。
- 接收原版状态变化。
- 将原版数据转换为表现层需要的只读数据。

不得在Adapter中复制或重新实现原版业务规则。

### 4.2 接口设计

根据P0中识别出的真实原版接口，建立统一接口。

建议接口包括：

游戏状态：
- getGameState()
- getCurrentScene()
- getCurrentTurn()

城市：
- getCities()
- getCity(cityId)
- selectCity(cityId)
- getCityConnections(cityId)
- getCityActions(cityId)
- executeCityAction(cityId, action)

武将：
- getOfficers(cityId)
- getOfficer(officerId)
- selectOfficer(officerId)

战斗：
- getBattleState()
- getBattleUnits()
- getMovementRange(unitId)
- getAttackRange(unitId)
- moveUnit(unitId, target)
- attackUnit(unitId, target)

回合：
- endTurn()

以上是建议接口，必须依据原版实际代码映射。

如果某项能力不存在，必须说明原因，不得创建虚假的成功返回。

### 4.3 数据访问约束

表现层尽量使用只读数据。

禁止：
- 直接修改原版城市对象。
- 直接修改原版武将对象。
- 直接修改原版部队对象。
- 在3D场景中计算游戏规则。

需要执行操作时，必须调用Adapter。

如果原版对象允许直接修改，应通过原版规定的业务函数进行修改。

### 4.4 数据映射

建立表现层数据映射机制。

例如城市：

{
    id: originalCityId,
    name: originalCityName,
    ownerId: originalOwnerId,
    position: {
        x: originalX,
        y: originalY
    }
}

以上仅表示目标数据结构。

实际字段必须来自原版真实数据。

映射层只负责转换字段和格式，不允许改变数据含义。

## 五、事件和状态同步机制

建立统一的EventManager。

负责将原版游戏状态变化通知表现层。

建议支持以下事件：

- GAME_INITIALIZED
- GAME_STATE_UPDATED
- CITY_SELECTED
- CITY_UPDATED
- CITY_OWNER_CHANGED
- OFFICER_UPDATED
- BATTLE_STARTED
- BATTLE_STATE_UPDATED
- UNIT_SELECTED
- UNIT_MOVED
- UNIT_ATTACKED
- BATTLE_FINISHED
- TURN_CHANGED

事件名称可以根据原版真实调用情况调整。

### 5.1 事件来源

优先通过原版逻辑现有的回调或事件机制获取变化。

如果原版没有事件系统：
- 使用Adapter包装原版操作入口。
- 在操作完成后读取真实状态。
- 根据状态变化发送表现层事件。

禁止在渲染循环中无条件重复读取全部游戏数据。

### 5.2 状态同步

建立统一状态同步流程：

原版游戏逻辑
    ↓
GameAdapter
    ↓
EventManager
    ↓
SceneManager / UI
    ↓
Three.js对象更新

要求：
- 事件不能直接修改游戏逻辑。
- 同一个状态变化不能重复处理。
- 场景切换后不能丢失必要事件。
- 渲染对象销毁后必须取消相关订阅。
- 重要状态以原版实时数据为准。

## 六、坐标转换体系

建立独立的CoordinateSystem。

本模块是后续战略地图和战斗地图的基础。

### 6.1 坐标系统分类

至少区分：

1. 原版地图逻辑坐标。
2. Three.js世界坐标。
3. Three.js屏幕坐标。
4. 战斗地图格子坐标。

不得混用不同坐标体系。

### 6.2 战略地图坐标

建立统一接口：

- mapToWorld()
- worldToMap()
- worldToScreen()

要求：
- 保留原版城市坐标。
- 通过统一比例、偏移和方向转换。
- 支持后续调整地图整体尺寸。
- 不允许为单个城市设置特殊转换逻辑。
- 保证转换可逆或具备明确的精度约束。

战略地图采用固定斜45°视角。

优先采用正交相机。

注意：逻辑地图坐标到世界坐标的转换与摄像机投影是两个不同过程，不得混为一个转换函数。

### 6.3 战斗地图坐标

建立统一接口：

- gridToWorld()
- worldToGrid()

必须保留原版战斗格子的行列关系。

即使战斗场景采用斜视角，格子逻辑坐标仍然保持原版形式。

### 6.4 坐标测试

至少验证：
- 原版城市坐标可以正确转换。
- 转换后的城市位置稳定。
- 坐标逆转换结果符合精度要求。
- 战斗格子转换正确。
- 屏幕缩放不会改变游戏逻辑坐标。

使用P0提取的真实数据进行测试。

## 七、场景管理体系

建立SceneManager。

本阶段先建立三个场景的框架：

### 7.1 WorldMapScene

负责战略地图场景。

本阶段只需要：
- 创建Scene。
- 创建Camera。
- 创建基础地面。
- 创建简单占位对象。
- 支持摄像机基础操作。

不要求完成真实城市和道路模型。

### 7.2 CityScene

负责城市管理场景。

本阶段只建立：
- 场景入口。
- 场景生命周期。
- 城市ID上下文。
- 城市UI挂载入口。

暂时不实现完整城市模型和菜单功能。

### 7.3 BattleScene

负责战斗场景。

本阶段只建立：
- 场景入口。
- Scene和Camera。
- 战斗状态上下文。
- 战斗UI挂载入口。

暂时不实现真实战斗地图和部队模型。

### 7.4 场景生命周期

统一支持：

- enter()
- update()
- render()
- exit()
- dispose()

实际函数名称可根据项目风格调整。

要求：
- 场景进入时初始化自身资源。
- 场景退出时释放自身资源。
- 不重复创建全局Renderer。
- 不重复注册全局事件。
- 不修改原版游戏状态。
- 切换场景时保留原版游戏状态。

### 7.5 场景切换

建立场景切换入口。

支持：

- 战略地图进入城市管理。
- 城市管理返回战略地图。
- 战略地图进入战斗。
- 战斗结束返回战略地图。

本阶段可以使用测试入口验证场景生命周期，但不得伪造真实游戏操作结果。

## 八、摄像机管理

建立CameraManager。

### 战略地图摄像机

要求：
- 固定斜45°视角。
- 不允许自由旋转。
- 支持平移。
- 支持缩放。
- 支持边界限制。
- 参数统一配置。

### 战斗摄像机

建立独立摄像机配置。

采用固定斜视角，后续用于战棋场景。

不要求本阶段实现完整战斗镜头效果。

### 城市管理场景

根据最终场景设计决定使用独立摄像机还是复用战略地图背景。

不能在本阶段过早锁定不必要的渲染方案。

## 九、输入管理

建立InputManager。

负责统一管理：
- 鼠标移动。
- 鼠标点击。
- 鼠标拖动。
- 鼠标滚轮。
- 键盘输入。

要求：
- 区分3D画布输入与HTML UI输入。
- UI弹窗打开时，不能让点击穿透到3D场景。
- 地图拖动不能误触发城市选择。
- 滚轮缩放不能影响UI滚动。
- 支持后续触摸屏扩展。

本阶段实现基础输入框架和事件分发，不实现完整游戏操作。

## 十、资源管理

建立AssetManager。

负责：
- GLTF/GLB模型加载。
- 纹理加载。
- 材质管理。
- 加载缓存。
- 加载失败处理。
- 资源释放。

要求：
- 相同资源避免重复加载。
- 明确资源所有权。
- 场景释放时正确处理资源引用。
- 不得提前释放仍被其他场景使用的共享资源。
- 支持后续城市、旗帜、地形和部队模型扩展。

本阶段可以使用基础几何体验证资源和渲染流程。

## 十一、UI与3D画布集成

建立统一的应用布局。

要求：
- Three.js Canvas作为3D展示区域。
- HTML/CSS负责菜单和弹窗。
- 两者坐标和尺寸正确同步。
- UI层级高于3D画布。
- 弹窗打开时正确管理输入事件。
- 窗口大小变化时自动调整。

不要将普通文字菜单和大量表单制作成3D模型。

城市管理和战斗UI继续采用HTML/CSS。

## 十二、基础运行验证

本阶段结束时必须有一个可以运行的基础版本。

至少完成：

1. 原版游戏能够正常启动。
2. Three.js能够正常初始化。
3. WebGLRenderer正常工作。
4. 基础3D场景正常显示。
5. 可以切换三个场景框架。
6. 可以读取原版游戏状态。
7. 可以读取真实城市数据。
8. 坐标转换测试通过。
9. 事件订阅和取消正常。
10. 窗口尺寸变化正常。
11. 资源加载和释放正常。
12. 不影响原版核心游戏逻辑。

可以使用简单几何体作为测试对象，不需要正式美术资源。

## 十三、性能和稳定性

- 不重复创建Renderer。
- 不重复创建动画循环。
- 不重复加载相同资源。
- 正确释放场景对象。
- 避免事件监听器泄漏。
- 避免渲染层直接操作DOM之外的原版内部状态。
- 合理管理requestAnimationFrame。
- 支持浏览器窗口变化。
- 控制设备像素比。
- 处理WebGL初始化失败。

完成以下实际交付：

1. Three.js接入。
2. RenderManager。
3. GameAdapter。
4. EventManager。
5. CoordinateSystem。
6. SceneManager。
7. CameraManager。
8. InputManager。
9. AssetManager。
10. 三个基础场景框架。
11. 基础3D测试场景。
12. 坐标转换测试。
13. 适配层测试。
14. 项目运行和验证说明。

所有模块必须根据现有项目实际结构落地，不要求机械套用建议目录。

## 十五、P1验收标准

### 架构
- Three.js接入成功。
- 模块职责明确。
- 原版逻辑与表现层解耦。
- 三个场景可以统一管理。

### 数据
- 能读取原版真实游戏状态。
- 能读取原版真实城市数据。
- 不存在渲染层第二套权威游戏数据。

### 坐标
- 战略地图坐标转换正确。
- 战斗格子坐标转换正确。
- 坐标转换具有测试依据。

### 交互
- 输入事件可以统一管理。
- UI和3D画布输入互不干扰。
- 场景生命周期正确。

### 稳定性
- 项目正常启动。
- 原版游戏逻辑不受影响。
- 不存在明显资源泄漏。
- 不存在重复渲染循环。

### 本阶段不要求
- 不要求完成真实城市模型。
- 不要求完成战略地图美术。
- 不要求完成城市管理功能。
- 不要求完成战斗地图。
- 不要求完成战斗动画。

这些属于后续阶段任务。

# 十六、阶段执行约束

1. 只实施当前指定阶段的任务。
2. 不提前开发后续阶段的功能。
3. 开始前检查P0阶段的交付物。
4. 以真实源码为依据，不猜测原版接口。
5. 优先复用现有代码。
6. 不允许修改无关的原版逻辑。
7. 不允许用模拟数据代替原版数据。
8. 当前阶段必须实现实际功能，而不是只输出方案。
9. 完成后运行相关测试。
10. 对照阶段验收标准逐项检查。
11. 记录实际修改的文件和接口。
12. 记录尚未解决的问题。
13. 保持项目可以正常启动和运行。
14. 不得以TODO或空函数冒充完成。
15. 如果发现原版行为与预期不一致，先分析并报告，不得自行改变游戏规则。

阶段结束时输出：

- 完成内容。
- 修改文件。
- 新增接口。
- 测试结果。
- 验收情况。
- 遗留问题。
- 下一阶段前置条件。

不得擅自进入下一阶段，等待用户确认后再继续。
